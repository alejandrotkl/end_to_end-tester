# 🔗 Playwright Link Tester

Автоматическое **end-to-end тестирование списка ссылок** с помощью [Playwright](https://playwright.dev).  
Загружаете файл со ссылками — программа сама открывает каждую в браузере, проверяет её работоспособность и выводит подробный отчёт.

</div>

> [!IMPORTANT]
> Для работы требуется установленный **Node.js** (LTS-версия) и браузер **Chromium**, который ставится отдельной командой (см. раздел [Установка](#️-установка-и-запуск)).

> [!TIP]
> Весь вывод программы — консоль, лог-файл и сообщения об ошибках — на **русском языке**.

> [!NOTE]
> Проект работает одинаково на **Windows, macOS и Linux** — он написан на Node.js и Playwright, которые кросс-платформенны. Ниже приведены команды установки для каждой ОС.

> [!NOTE]
> Помимо запуска из консоли, проект можно поднять как **HTTP API-сервер** — см. раздел [Запуск как сервер (API)](#-запуск-как-сервер-api).

## ℹ️Что делает программа

Ссылки проверяются по очереди — более приоритетные (см. [Формат файла со ссылками](#-формат-файла-со-ссылками)) раньше остальных. Для каждой ссылки программа:

1. Открывает страницу в headless-браузере (Chromium), ожидая ответ не дольше её таймаута (по умолчанию 30 с, настраивается по ссылке)
2. Проверяет, что получен ответ и **HTTP статус меньше 400** (если получен **403** или вместо страницы показана форма входа — пытается войти на сайт и проверить страницу повторно, см. [Проверка ссылок за авторизацией](#-проверка-ссылок-за-авторизацией-http-403-и-страницы-входа))
3. Проверяет, что элемент `<body>` виден на странице
4. Проверяет, что заголовок страницы (`<title>`) не пустой
5. Замеряет **время загрузки** и **общее время обработки** ссылки
6. Записывает результат в консоль и текстовый лог (в серверном режиме — ещё и в файл прогресса, доступный через API/веб-интерфейс в реальном времени)

## ⚙️Установка и запуск

### 1. Установите Node.js (LTS), если он ещё не установлен

**Windows** (PowerShell):

```powershell
winget install OpenJS.NodeJS.LTS
```

**macOS** (через [Homebrew](https://brew.sh)):

```bash
brew install node
```

**Linux** (Debian/Ubuntu):

```bash
sudo apt update && sudo apt install -y nodejs npm
```

На других дистрибутивах используйте свой пакетный менеджер (`dnf`, `pacman` и т.д.) либо [официальный установщик](https://nodejs.org).

После установки перезапустите терминал и проверьте версию: `node -v` (нужна версия 18 или новее).

### 2. Установите зависимости проекта

Команда одинакова на всех ОС:

```bash
npm install
```

### 3. Установите браузер Chromium для Playwright

```bash
npx playwright install chromium
```

> [!IMPORTANT]
> **Только для Linux:** Chromium требует системные библиотеки, которых нет по умолчанию на многих дистрибутивах. Если при запуске тестов Playwright ругается на отсутствующие библиотеки (`libnss3`, `libatk` и т.п.), выполните:
>
> ```bash
> sudo npx playwright install-deps
> ```
>
> Либо сразу поставьте браузер вместе с зависимостями: `npx playwright install --with-deps chromium`.

### 4. Подготовьте файл со ссылками

См. раздел [Формат файла со ссылками](#-формат-файла-со-ссылками).

### 5. Запустите тесты, указав файл со ссылками

Команды одинаковы на всех ОС:

```bash
npm test -- --file links.txt
```

Либо запустите без аргумента — программа сама спросит путь к файлу:

```bash
npm test
```

> [!TIP]
> Полный путь указывать необязательно. Если файл не найден в текущей папке, программа автоматически поищет его по имени в папке проекта, на Рабочем столе, в Документах и Загрузках. Если найдётся несколько файлов с таким именем — будет предложено выбрать нужный из списка.

## 📄 Формат файла со ссылками

Поддерживаются два формата.

**Текстовый файл (`.txt`)** — одна ссылка на строку. Строки, начинающиеся с `#`, игнорируются:

```txt
# Мои ссылки для проверки
https://example.com
https://playwright.dev
```

**JSON-файл (`.json`)** — массив ссылок или объект с полем `links`. Каждый элемент массива — либо просто строка (обычная ссылка со значениями по умолчанию), либо объект со своим таймаутом (и, при необходимости, приоритетом):

```json
{
  "links": [
    "https://example.com",
    {
      "url": "https://slow-site.example.com",
      "timeoutMs": 60000
    }
  ]
}
```

- Приоритет — это просто **позиция ссылки в списке**: чем раньше она стоит, тем раньше проверяется (в веб-интерфейсе порядок меняется перетаскиванием). Задавать его отдельно не нужно — достаточно порядка элементов в массиве. При необходимости позицию можно переопределить явно, добавив в объект ссылки числовое поле `priority` (чем меньше число, тем раньше проверка) — это не обязательно и нужно только для программного управления порядком без переупорядочивания самого массива.
- `timeoutMs` — сколько ждать ответа страницы, прежде чем считать её ошибочной (по умолчанию `30000`, т.е. 30 секунд). Полезно увеличить для страниц, которые обычно грузятся долго, — иначе они будут ошибочно помечаться как упавшие раньше времени. Можно указать и в секундах — если число меньше `1000`, оно считается секундами (например, `60` — то же самое, что `60000`).
- `require` — необязательные доп. условия успеха: на странице должен найтись элемент по пути тегов (`path`), тегу (`tag`), классам (`classes`) и/или тексту (`text`). В веб-интерфейсе задаётся кнопкой ⚙ у ссылки.

Пример с доп. условием:

```json
[
  {
    "url": "https://example.com/page",
    "timeoutMs": 30000,
    "require": [
      { "kind": "element", "path": "tbody", "tag": "td", "classes": "status", "text": "OK" }
    ]
  }
]
```

> [!WARNING]
> Ссылка обязательно должна начинаться с `http://` или `https://`, иначе она будет проигнорирована.

## 🔐 Проверка ссылок за авторизацией (HTTP 403 и страницы входа)

Программа распознаёт, что ссылка доступна только авторизованным пользователям, в двух случаях:

- страница отвечает **HTTP 403** (доступ запрещён);
- страница отвечает **HTTP 200**, но вместо содержимого показывает **форму входа** (сайт молча редиректит на логин или рисует его на месте — определяется по видимому полю пароля). Без этой проверки такая ссылка выглядела бы «рабочей», хотя сама страница не открылась.

В обоих случаях программа не считает это сразу ошибкой, а пытается войти на сайт и проверить страницу повторно:

1. Определяется домен ссылки (например, `example.com`).
2. Ищутся сохранённые данные для входа по этому домену.
3. Если данные есть — программа открывает страницу входа (`loginUrl`; если он не задан, а форма логина уже на экране — заполняет её прямо там), вводит логин и пароль, отправляет форму и **возвращается на исходную ссылку уже в авторизованной сессии**, после чего проверяет её как обычно. Если после входа сайт снова показывает форму логина — проверка помечается ошибкой с объяснением.
4. Если данных нет:
   - **в консольном режиме** (`npm test`) — программа спросит логин и пароль прямо в терминале и, если вы согласитесь, сохранит их для следующих запусков;
   - **в серверном режиме** — проверка такой ссылки завершится с пометкой «требуется вход», а в веб-интерфейсе появится баннер со ссылкой на страницу [«Доступы для входа»](/credentials.html): после сохранения логина/пароля затронутые ссылки перепроверяются в той же задаче (`POST /api/v1/jobs/:id/recheck`). Данные можно настроить и через API (см. [Данные для входа](#данные-для-входа-при-http-403)) — дальше все проверки (в т.ч. плановые) используют их автоматически.

Поля формы входа определяются автоматически по типовым признакам (`input[type="password"]` для пароля, кнопка с текстом «Войти»/«Log in» и т.д. для отправки). Если у сайта нестандартная форма, можно явно указать свои CSS-селекторы полей — см. описание полей `usernameSelector`/`passwordSelector`/`submitSelector` в разделе про API.

Данные для входа хранятся в отдельном JSON-файле на диске (`.credentials/`, не попадает в Git — как и `.env`), пароль в нём не шифруется. В консольном режиме — один общий файл (`.credentials/cli.json`); на сервере — свой файл на каждый API-ключ, чтобы данные разных клиентов не пересекались.

> [!WARNING]
> Ввод пароля в консоли не скрывается точками — это ограничение простого текстового ввода без дополнительных библиотек. Не запускайте консольный режим там, где экран виден посторонним, если собираетесь вводить реальный пароль.

## Уведомления об ошибках в Telegram

Сервер может присылать администратору сообщение в Telegram:

- **сразу, как только ссылка не прошла проверку** — не дожидаясь конца всей задачи. Сообщение короткое: URL и одна строка с причиной;
- если **вся задача не выполнилась** (например, сбой Playwright при старте) — отдельным сообщением с текстом ошибки.

Настраивается на вкладке **«Уведомления»** (`/notifications.html`): токен бота ([@BotFather](https://t.me/BotFather)), chat id и переключатель включения. Там же можно отправить тестовое сообщение.

API:

- `GET /api/v1/notifications` — текущие настройки (токен не целиком, только признак и последние 4 символа);
- `PUT /api/v1/notifications` — сохранить `{ "botToken": "...", "chatId": "...", "enabled": true }` (`botToken` можно не передавать повторно);
- `POST /api/v1/notifications/test` — тестовое сообщение;
- `DELETE /api/v1/notifications` — удалить настройки.

Настройки хранятся в `.notifications/<ключ>.json` (не в Git), отдельно для каждого API-ключа. Сбой отправки в Telegram только пишется в лог и не влияет на проверку ссылок.

## 🌐 Запуск как сервер (API)

Помимо запуска из консоли, проект можно развернуть как HTTP-сервер: он принимает запросы с API-ключом, ставит проверку ссылок в очередь и отдаёт результат в JSON. Сервер умеет как выполнять разовые проверки по запросу, так и сам, по встроенному расписанию, периодически перепроверять список ссылок (см. [Плановые проверки по расписанию](#плановые-проверки-по-расписанию)) — внешний cron или другая система для этого не нужны.

### Как это устроено

Каждый запрос на проверку — это отдельная задача (job):

1. Клиент отправляет список ссылок (или файл) со своим API-ключом → сервер сразу отвечает id задачи и статусом `pending`.
2. Сервер ставит задачу в очередь и запускает для неё отдельный процесс Playwright — лог и результат каждой задачи хранятся в собственной папке `.jobs/<id>`, задачи друг другу не мешают.
3. Клиент периодически запрашивает статус по id, пока он не станет `completed` (или `failed`), и затем отдельным запросом забирает результаты.

Так как проверка через браузер может занимать заметное время, API асинхронный — сразу результат не возвращается.

### Запуск

```bash
npm install
npx playwright install chromium
cp .env.example .env
```

Откройте `.env` и задайте как минимум `API_KEYS` — без него сервер не пропустит ни один запрос к `/api/v1/*` (подробности и формат — прямо в `.env.example`).

```bash
npm run server
```

Сервер поднимется на порту из `PORT` (по умолчанию `3000`). Проверить, что он жив:

```bash
curl http://localhost:3000/health
```

### Веб-интерфейс

Пользоваться сервером необязательно через консоль — на самом сервере есть простая веб-страница, ничего дополнительно ставить не нужно. Откройте в браузере:

```
http://localhost:3000/
```

Введите свой API-ключ (сохраняется только в этом браузере, в `localStorage`) и нажмите «Сохранить». В шапке две страницы:

- **Проверка** (`/`) — список ссылок и панель «Сейчас выполняется».
- **Логи задач** (`/logs.html`) — история задач и подробные результаты проверок (отдельная страница, не на одной с проверкой).

На странице проверки сверху вниз:

- **Проверка ссылок** — общий список ссылок и кнопки в одном ряду: разовая проверка («Проверить один раз»), интервал и настройка/запуск/остановка плановой проверки (см. [Плановые проверки по расписанию](#плановые-проверки-по-расписанию)).
- **Сейчас выполняется** — всегда на странице: время начала текущей проверки, время следующей по расписанию, какая ссылка проверяется сейчас, сколько уже проверено и результаты уже готовых ссылок. Обновляется каждые 1.5 секунды. Панель общая для всех, кто открыл страницу с одним и тем же API-ключом: активная задача берётся из общего списка задач ключа, поэтому все устройства видят одну и ту же текущую проверку.

На странице «Логи задач» — список всех задач ключа (обновляется раз в 5 секунд) с удалением и кнопкой «Результаты»; подробная таблица по ссылкам открывается под списком.

Ссылки добавляются по одной кнопкой «+ Добавить ссылку» в постоянный список: у каждой ссылки — своё поле таймаута (в секундах), ручка ⠿ для перетаскивания и кнопка ✕ для удаления. Приоритет — это позиция ссылки в этом списке (номер слева): более высокие в списке ссылки проверяются раньше, порядок меняется перетаскиванием ряда за ручку ⠿ в нужное место. Список остаётся в поле и после запуска проверки — его можно тут же запустить повторно или сохранить как расписание. Файл `.txt`/`.json` можно загрузить отдельным полем — его содержимое сразу подставится в список ссылок, где его можно проверить и отредактировать перед запуском (сам файл никуда не отправляется). Время загрузки и общее время в результатах показывается в секундах, а при больших значениях — в минутах и секундах, а не в миллисекундах.

Список ссылок хранится не только в браузере, но и на сервере — на каждый API-ключ свой список (см. `GET`/`PUT /api/v1/links-draft`). Поэтому если открыть страницу с одним и тем же ключом на двух устройствах (например, с телефона и с компьютера), оба увидят один и тот же список и правки друг друга — страница подтягивает изменения раз в 3 секунды. Пока вы печатаете в поле, чужие правки не подменяют его содержимое — они применятся, как только вы закончите редактировать. Это простая синхронизация «кто сохранил последним, тот и прав», без слияния правок по отдельным полям.

Страница обращается к тому же API (`/api/v1/*`), так что у неё не больше и не меньше возможностей, чем описано в этом README — просто без `curl`.

### Аутентификация

Каждый запрос к `/api/v1/*` должен содержать API-ключ в одном из заголовков:

```
X-API-Key: <ключ>
```

либо

```
Authorization: Bearer <ключ>
```

Ключи задаются в `.env` переменной `API_KEYS` в формате `имя:ключ` через запятую — так можно выдать отдельный ключ каждому клиенту/команде и видеть, кто создал задачу. Задачи одного ключа не видны по другому ключу.

### Эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/health` | Проверка, что сервер жив (без авторизации) |
| `POST` | `/api/v1/jobs` | Создать задачу проверки ссылок |
| `GET` | `/api/v1/jobs` | Список своих задач |
| `GET` | `/api/v1/jobs/:id` | Статус и сводка по задаче |
| `GET` | `/api/v1/jobs/:id/progress` | Прогресс задачи в реальном времени (какая ссылка проверяется сейчас, результаты уже готовых) — работает при любом статусе, в отличие от `/results` |
| `GET` | `/api/v1/jobs/:id/results` | Полные результаты (только когда статус `completed`) |
| `DELETE` | `/api/v1/jobs` | Удалить все завершённые задачи текущего API-ключа (выполняющиеся не трогает; независимо от автоочистки) |
| `DELETE` | `/api/v1/jobs/:id` | Удалить задачу и её данные |
| `POST` | `/api/v1/jobs/:id/recheck` | Повторно проверить часть ссылок внутри существующей задачи (после сохранения логина) |
| `PUT` | `/api/v1/schedule` | Настроить плановую проверку (список ссылок + интервал) |
| `GET` | `/api/v1/schedule` | Статус плановой проверки |
| `POST` | `/api/v1/schedule/run` | Запустить плановую проверку прямо сейчас (вручную) |
| `DELETE` | `/api/v1/schedule` | Остановить и удалить плановую проверку |
| `GET` | `/api/v1/credentials` | Список настроенных доменов для входа (без паролей) |
| `PUT` | `/api/v1/credentials/:domain` | Добавить/обновить данные для входа по домену |
| `DELETE` | `/api/v1/credentials/:domain` | Удалить данные для входа по домену |
| `GET` | `/api/v1/notifications` | Настройки Telegram-уведомлений (токен не целиком) |
| `PUT` | `/api/v1/notifications` | Сохранить токен бота, chat id и флаг enabled |
| `POST` | `/api/v1/notifications/test` | Отправить тестовое сообщение в Telegram |
| `DELETE` | `/api/v1/notifications` | Удалить настройки уведомлений |
| `GET` | `/api/v1/links-draft` | Общий (на все устройства с этим API-ключом) список ссылок из веб-интерфейса |
| `PUT` | `/api/v1/links-draft` | Сохранить общий список ссылок (вызывается веб-интерфейсом автоматически при правках) |

Создать задачу можно двумя способами — списком ссылок в JSON-теле запроса или загрузив файл `.txt`/`.json` (тот же формат, что и в консольном режиме, см. [Формат файла со ссылками](#-формат-файла-со-ссылками)).

**Список ссылок в теле запроса:**

```bash
  -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "links": ["https://example.com", "https://playwright.dev"] }'
```

**Загрузка файла:**

```bash

  -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY" \

```

Оба варианта отвечают `202 Accepted`:


### Плановые проверки по расписанию

Кроме разовых задач через `/api/v1/jobs`, сервер умеет сам, без внешнего вызова, периодически перепроверять один и тот же список ссылок — у каждого API-ключа может быть настроено собственное расписание.

Особенность: интервал отсчитывается не по жёсткому времени суток, а **от момента завершения предыдущей проверки**. Поэтому если запустить проверку вручную (`POST /api/v1/schedule/run`) в промежутке между плановыми запусками, следующий плановый запуск просто сдвинется на интервал вперёд от этого ручного — двойной проверки подряд не будет.

**Настроить расписание** (создаёт его, если ещё не было, либо обновляет список ссылок/интервал существующего, и сразу выполняет первую проверку):

```bash
curl -X PUT http://localhost:3000/api/v1/schedule \
  -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "links": ["https://example.com", "https://playwright.dev"], "intervalMinutes": 5 }'
```

`intervalMinutes` необязателен — если не указать, используется значение `SCHEDULE_INTERVAL_MS` из `.env` (по умолчанию 5 минут). Минимальный интервал — 1 минута. Вместо JSON-тела можно, как и в `/api/v1/jobs`, загрузить файл: `-F "file=@links.txt"`.

**Посмотреть статус расписания:**

```bash
curl -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY" http://localhost:3000/api/v1/schedule
```

```json
{
  "apiKeyName": "team-a",
  "intervalMs": 300000,
  "enabled": true,
  "totalLinks": 2,
  "lastJobId": "b1f2e3a4-2f3a-4c1a-9c3a-6a2e8f6b7c9d",
  "lastRunAt": "2026-07-08T08:00:00.000Z",
  "nextRunAt": "2026-07-08T08:05:00.000Z"
}
```

Результаты последней плановой проверки читаются как у обычной задачи — по `lastJobId` через `GET /api/v1/jobs/:id/results`.

**Проверить прямо сейчас, не дожидаясь таймера** (и сразу же сдвинуть следующий плановый запуск, как описано выше):

```bash
curl -X POST http://localhost:3000/api/v1/schedule/run -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY"
```

**Остановить плановые проверки** (удаляет расписание и сохранённый список ссылок; сами прошлые задачи и их результаты остаются):

```bash
curl -X DELETE http://localhost:3000/api/v1/schedule -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY"
```

> [!NOTE]
> При перезапуске сервера все ранее настроенные и включённые расписания возобновляются автоматически: сервер сразу выполняет свежую проверку и продолжает обычный цикл — точная фаза интервала, на которой сервер был остановлен, не сохраняется.

### Автоматическая очистка старых логов

Каждая задача (обычная или плановая) хранит свой лог, результат и скриншоты в отдельной папке `JOBS_DIR/<id>`. При плановых проверках, например раз в 5 минут, это больше 8000 папок в месяц — без очистки диск сервера рано или поздно закончится.

Поэтому сервер сам, без дополнительной настройки, раз в сутки проверяет возраст завершённых задач (`completed`/`failed`) и удаляет те, что старше срока хранения. По умолчанию срок хранения — 30 дней, то есть по факту логи каждой задачи «живут» около месяца. Задачи, которые ещё выполняются, никогда не удаляются независимо от возраста.

Настраивается через `.env`:

- `LOG_RETENTION_DAYS` — сколько дней хранить логи завершённых задач (по умолчанию `30`)
- `CLEANUP_INTERVAL_MS` — как часто проверять и удалять устаревшие (по умолчанию раз в сутки)

Первая проверка запускается сразу при старте сервера (на случай, если он был выключен дольше срока хранения), дальше — по интервалу. В логе сервера при удалении появится строка вида `[очистка логов] Удалено старых задач (старше 30 дн.): 12.`.

> [!NOTE]
> Список ссылок, сохранённый для плановой проверки (не лог, а текущая настройка расписания), этой очисткой не затрагивается — он живёт, пока расписание не остановлено через `DELETE /api/v1/schedule`.

### Данные для входа (при HTTP 403)

Если проверяемая ссылка требует авторизации (отвечает HTTP 403 или показывает форму входа вместо содержимого), сервер может сам залогиниться и повторить проверку — но только если для домена этой ссылки настроены данные для входа (подробнее о самом механизме — в разделе [Проверка ссылок за авторизацией](#-проверка-ссылок-за-авторизацией-http-403-и-страницы-входа)). Самый простой способ настроить их — веб-интерфейс: когда проверка встречает такую ссылку, на странице автоматически всплывает окно ввода логина и пароля, а после сохранения затронутые ссылки перепроверяются. Задать данные можно и заранее через API — дальше все проверки (ручные и плановые) используют их автоматически. Данные привязаны к API-ключу: у разных клиентов свои наборы, один не видит и не может изменить данные другого.

Поле `loginUrl` (адрес страницы входа) необязательно: если сайт сам показывает форму логина на проверяемой странице, его можно не указывать — форма будет заполнена там, где она обнаружена.

**Настроить (или обновить) данные для домена:**

```bash
curl -X PUT http://localhost:3000/api/v1/credentials/example.com \
  -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "loginUrl": "https://example.com/login", "username": "user@example.com", "password": "secret" }'
```

Необязательные поля `usernameSelector`, `passwordSelector`, `submitSelector` — CSS-селекторы для нестандартной формы входа (по умолчанию поля определяются автоматически: пароль — `input[type="password"]`, кнопка — по типу `submit` или тексту «Войти»/«Log in» и т.п.):

```bash
curl -X PUT http://localhost:3000/api/v1/credentials/example.com \
  -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "loginUrl": "https://example.com/login",
    "username": "user@example.com",
    "password": "secret",
    "usernameSelector": "#email",
    "passwordSelector": "#pass",
    "submitSelector": "button.login-submit"
  }'
```

**Список настроенных доменов** (пароли не возвращаются):

```bash
curl -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY" http://localhost:3000/api/v1/credentials
```

**Удалить данные для домена:**

```bash
curl -X DELETE http://localhost:3000/api/v1/credentials/example.com -H "X-API-Key: CHANGE_ME_LONG_RANDOM_KEY"
```

В результатах проверки (`GET /api/v1/jobs/:id/results` и таблица в веб-интерфейсе) у каждой ссылки есть поля `usedLogin` (вход был выполнен) и `needsLogin` (страница требует вход, но данные для домена не настроены).

### Запуск в Docker

Проще всего разворачивать сервер на любом Linux-сервере через Docker — образ уже содержит Chromium и все системные зависимости, ничего доустанавливать вручную не нужно:

```bash
cp .env.example .env   # заполните API_KEYS
docker compose up -d --build
```

Сервер станет доступен на порту `3000` (чтобы сменить порт, достаточно поменять `PORT` в `.env` — `docker-compose.yml` подставит его автоматически). Данные задач сохраняются в именованном томе `jobs-data`, поэтому переживают пересборку и перезапуск контейнера.

> [!IMPORTANT]
> Версия в `Dockerfile` (`ARG PLAYWRIGHT_VERSION`) должна совпадать с версией `@playwright/test` из `package-lock.json` — иначе Playwright внутри контейнера не найдёт браузер. При обновлении Playwright обновите обе версии.

### Настройки сервера

Все настройки — в `.env` (см. `.env.example`):

- `PORT` — порт сервера
- `API_KEYS` — обязательный список ключей `имя:ключ` через запятую
- `MAX_CONCURRENT_JOBS` — сколько задач может выполняться одновременно (по умолчанию `1`)
- `MAX_LINKS_PER_JOB` — максимум ссылок в одной задаче
- `MAX_UPLOAD_BYTES` — максимальный размер запроса на создание задачи (файл или JSON-тело)
- `JOBS_DIR` — папка, где хранятся данные задач
- `SCHEDULE_INTERVAL_MS` — интервал плановых проверок по умолчанию в миллисекундах, если клиент не указал свой `intervalMinutes` (по умолчанию `300000` — 5 минут)
- `LOG_RETENTION_DAYS` — сколько дней хранить логи завершённых задач, прежде чем сервер удалит их автоматически (по умолчанию `30`)
- `CLEANUP_INTERVAL_MS` — как часто сервер проверяет и удаляет устаревшие логи, в миллисекундах (по умолчанию раз в сутки)
- `CREDENTIALS_DIR` — папка, где хранятся данные для входа по доменам, отдельный файл на каждый API-ключ (по умолчанию `.credentials`)
- `NOTIFICATIONS_DIR` — папка настроек Telegram-уведомлений, отдельный файл на каждый API-ключ (по умолчанию `.notifications`)

> [!NOTE]
> Консольный режим (`npm test`) и серверный режим (`npm run server`) — два независимых способа использовать один и тот же движок проверки ссылок. Для разовой локальной проверки удобнее консоль; сервер нужен, когда проверку должны запускать другие системы по API.

## 📊 Логи и результаты

Во время прогона в консоли построчно выводится результат по каждой ссылке:

```
[УСПЕХ] https://example.com | HTTP 200 | загрузка: 445 мс | всего: 481 мс
[ОШИБКА] https://broken-site.com | HTTP нет ответа | загрузка: 0 мс | всего: 2144 мс | ...

--- Итоги ---
Всего: 2 | Успешно: 1 | Ошибок: 1
Среднее время загрузки: 223 мс | Среднее общее время: 1313 мс
Файл лога: test-results/links.log
```

Полный лог сохраняется в файл:

```
test-results/links.log
```

> [!NOTE]
> На Windows путь в выводе будет отображаться с обратным слешем (`test-results\links.log`) — это не ошибка, а стандартное поведение Node.js на этой ОС.

При падении теста Playwright также сохраняет скриншот страницы в папку `test-results` — его можно открыть напрямую, без сервера.

> [!NOTE]
> В серверном режиме (см. [Запуск как сервер (API)](#-запуск-как-сервер-api)) лог и скриншоты каждой задачи сохраняются отдельно, в `.jobs/<id>/`, а не в общей `test-results/` — так параллельные задачи не перезаписывают файлы друг друга.
